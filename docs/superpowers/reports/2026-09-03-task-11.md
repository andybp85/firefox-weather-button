## Plan errors found and corrected

1. **The gust's colour never reached the page.** The plan's step 4 put
   `color: var(--wind-colour, var(--ink))` on `.reading, .note` only, while step 5 set `--wind-colour` on a bare
   `<span>` inside `#wind-direction`. A custom property set on the span has no `color` declaration on the span to
   consume it: the span inherits the computed colour of `.note`, which resolves `--wind-colour` on the *note*,
   where nothing sets it. The gust would have rendered in `--ink` on every panel. The plan's own test could not
   catch it — it asserted only that the inline custom property was written.
   Fixed: the span is built with `class="gust"` and `.plaque-wind .gust { color: var(--wind-colour) }` consumes it.
   The test now reads `#wind-direction .gust`.
2. **The unreported-plot test was vacuous** — the same failure mode as Task 10's. `rendered(...)` builds a fresh
   document, and `<g id="wind-plot">` is empty in `popup.html`, so `children.length === 0` passes against an
   untouched DOM. Verified: it passed before a line of `renderWindPlot` existed. Replaced with
   `render strikes the plot a measured wind left standing when the next one is unreported`, which renders a
   measured wind first and re-renders an unreported one into the same document. Same treatment for the colour:
   `render drops the force colour from a speed nobody measured` re-renders rather than checking a virgin element.
3. **The shaft test checked two of four coordinates, and mixed a string with a number.** The plan asserted
   `[shaft.getAttribute('x2'), Math.round(Number(shaft.getAttribute('y2')))]` against `['44', 14]`, which cannot
   catch `from`/`to` or `x`/`y` being crossed in `buildShaft` — the only thing this test exists to check.
   Replaced with all four coordinates read back as numbers.
4. **Spec behaviour the plan omitted.** The spec's wind-plaque section says the direction line reads `variable`,
   `no direction` or `unreported` "in `--muted`" — a quieter step than the `--ink` of a line that names a compass
   point. Neither the plan's CSS nor its `renderWindDirection` mentions it, and Task 11 is the last task that
   touches this code, so it would never have shipped. Implemented as `.note.no-heading` toggled by
   `renderWindDirection`, with a test that also proves the class comes back off on a re-render.
   `--muted` clears AA on `--tile` (the plaque ground), which is why it is safe here and not on `--panel`.

## Deviations from the plan's snippets, for the tree

- `renderWind` calls `renderWindDirection` on all three states rather than duplicating a `write(...)` for calm and
  unreported: the muted-class decision has to happen on every path, and one function owning the whole line is
  cheaper to read than three places that each remember to set a class.
- `buildGust` was extracted from `renderWindDirection` so the latter stays a single concept.
- `describeSource`'s two guards were folded into `namesAHeading` + one expression, because
  `renderWindDirection` needs the same predicate and spelling it twice is a decision waiting to drift.

## Concerns

- **A barb can graze a cardinal letter.** A mark's tip reaches radius √(36.3² + 10.91²) ≈ 37.9, and the compass
  ring is r 38, so barbs touch the ring by design. For bearings around 348–352° a barb tip lands within a
  pixel or two of the `N` glyph's right edge. Both sets of coordinates are the spec's, so nothing was changed;
  flagging it so a reviewer with a browser can judge it rather than re-derive it.
- **Mark coordinates are emitted at full float precision** (`points="65.21377... ,22.79..."`). Harmless to SVG and
  consistent with how `renderSky` writes its shapes, but the attribute strings are long. Rounding would be a
  cross-plaque change, so it was left alone.
- The gust is drawn in its own force colour on an 11px line. `beaufort.js` already records that force 12's dark
  value falls short of 4.5:1 on `--tile` (4.15:1) — a known, documented exception, now reachable through this
  plaque's gust text.
